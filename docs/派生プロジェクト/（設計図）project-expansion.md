# 派生プロジェクト促進システム / Project Expansion Framework

## 0. 哲学 / Philosophy
**「1つのプロジェクトは、1つの目的で終わらない。本当に良い設計は、必ず次の問いを生み出す。」**

開発の過程で「これ、別のプロジェクトでも使えるのでは？」「この仕組みだけ切り出したら面白いのでは？」という瞬間が必ず来る。その瞬間を見逃さず、衝動が冷めないうちに「種」として記録し、育てる仕組みが本フレームワークである。

アイデアは形になる前に消える。記録だけが残る。

---

## 2. Concept (比喩を用いた説明)
**「木の年輪」**

木は1本だが、成長するたびに年輪が増える。年輪の1つひとつは独立した記録であり、同時に全体の一部でもある。派生プロジェクトとは、幹（親プロジェクト）から伸びた枝であり、それ自体がやがて幹になる。

どこから来たかが分かる。どこへ向かうかも分かる。

---

## 3. 言葉の定義

*   **親プロジェクト（Parent）**: 派生の起点となったプロジェクト。例：ATP（テスト環境構築）。
*   **派生プロジェクト（Derivative）**: 親から生まれた新しいプロジェクト。例：進化ループ、本フレームワーク。
*   **種（Seed）**: 「もしかしたらプロジェクトになるかも」という段階のアイデア。仕様書1枚で良い。
*   **発芽条件（Trigger）**: 種が実際のプロジェクトとして動き始める条件（「仕様書を書いたらスタート」など）。
*   **家系図（Lineage Map）**: 親子関係を可視化したもの。プロジェクト間のつながりを一目で把握できる。

---

## 4. 主要機能 (Main Features)

### 4.1. 種の記録（Seed Capture）

「これ面白いのでは？」と思った瞬間に、以下の3行だけ書く。書くだけで良い。育てるかどうかは後で決める。

```markdown
## 種：{仮のプロジェクト名}
- 何を解決するか：（1行）
- 親プロジェクト：（どこから生まれたか）
- 発芽条件：（何があったら始めるか）
```

この「3行」が揃わないうちは、アイデアではなく衝動である。3行書けたら、それは種になった。

### 4.2. 派生フォルダ構造（Derivative Folder Convention）

派生プロジェクトの仕様書は、**親プロジェクトの `docs/派生プロジェクト/` フォルダに置く**。

```text
（テスト環境構築）/
  └── docs/
      └── 派生プロジェクト/            ← 派生の置き場
          ├── （設計図）evolution-loop.md    ← ATP → 進化ループ
          ├── （設計図）project-expansion.md ← ATP → 本フレームワーク
          └── seeds.md                      ← まだ発芽していない種の一覧
```

**哲学**: 仕様書だけ持っておけば、コードはいつでも書ける。でも仕様書がなければ、アイデアは必ず消える。場所を決めることで、記録のコストをゼロにする。

### 4.3. 家系図の自動生成（Lineage Map）

`seeds.md` に種を記録し続けると、以下のような家系図が自然に育っていく。

```text
【家系図の例】
ATP（テスト環境構築）
├── 進化ループ（Evolution Loop）       🧬 開発中
│   └── プロンプト自動最適化エンジン  🌱 種
├── 派生プロジェクト促進システム（本書）🔵 仕様書完成
└── ATP汎用版（他プロジェクト対応）    🌱 種
    └── SaaS化（有料API提供）         🌱 種（孫）
```

親子関係が可視化されると、「この種は今すぐ育てるべきか、後で良いか」の判断が圧倒的に速くなる。

### 4.4. 発芽の判断基準（When to Start）

以下の**いずれか1つ**が当てはまれば、種はプロジェクトとして動かして良い。

1. **解決したい問題が具体的になった**: 「誰が・いつ・なぜ困るか」が言える。
2. **仕様書が1ページ書けた**: 書けたなら、それは作れるということ。
3. **監督が「やりたい」と言った**: 論理より衝動を優先する。AIはどうせついてくる。

逆に、以下の状態では始めない。
- 「面白そう」だけで具体性がゼロ
- 親プロジェクトがまだ未完成で混乱している最中

### 4.5. 引き継ぎ記録（Cross-Reference）

派生プロジェクトが独立したリポジトリになったとき、以下を `seeds.md` に記録する。

```markdown
| 派生名 | 状態 | リポジトリ | 親への参照 |
|--------|------|-----------|-----------|
| 進化ループ | 🔵開発中 | （同リポジトリ内） | ATP spec.md |
| ATP汎用版 | 🌱種 | 未作成 | ATP spec.md |
```

## 5. このフレームワーク自体の派生規則

**本フレームワーク（PEF）自体も派生プロジェクトである。**
ATPを作る過程で「作り方そのものをフレームワーク化する必要があった」から生まれた。

つまり、この仕様書を読んでいる誰かが「これをもっと汎用化したい」「別の言語で実装したい」と思ったなら、それは新しい派生の種である。記録してほしい。
