# @docs/spec.md (設計図) - Alchemist Test Pilot (ATP)

## 0. 哲学 / Philosophy
**「テストは入口に過ぎない。本当の仕事は、昨日より良くすることだ。」**

テストができるだけでは足りない。バグを見つけて直すだけでは足りない。本ツールは、**守る（修復）だけでなく、攻める（改良）AIである**。聖域を守りながら、コードを磨き、提案し、記録し、次の提案に活かす。人間が「気になったとき」にしか見ない部分を、常に見続ける。

## 2. Concept (比喩を用いた説明)
**「開発という飛行の『自動操縦士』であり、機体を磨き続ける『整備士』でもある。」**

バグが出たら直すのは当然だ。しかしそれで終わりにしない。正常に飛んでいる間も、機体の効率を分析し、改良案をエンジニアに提示し、採用されたものを記録し、次の提案に活かす。監督が何も言わなくても、昨日より良い状態を目指して動き続ける。これがテストAIではなく、**改良AIの定義**である。

---

## 3. 言葉の定義
*   **開発レジストリ**: `vault-alchemist/`（修正・開発を行う側のAI。GitHub: matsulinks/vault-alchemist）
*   **改良レジストリ**: 本ツール（AP）が管理するレポート・証拠・改善提案・採用記録を収める場所
*   **聖域（Sanctuary）**: すでに合格したテスト項目。ここが一つでも崩れることは「退行（Regression）」として絶対に許さない。
*   **ベースライン（基準状態）**: テストを開始する前の「正常な状態」の定義。**開発レジストリ側（vault-alchemistのdocs/spec.md）で定義・管理する責任を持つ。**
*   **世代（Generation）**: 改良ループが1サイクル完了するたびに増える番号。AIが自律的に育った「バージョン」の概念。

## 4. 主要機能 (Main Features)

### 4.1. 高解像度監視 (High-Res Monitoring)
*   **CLI検証**: `npm run test` 等の実行結果をリアルタイム監視し、53項目の生死を判定。
*   **UI/API検証**: Obsidianを自動操作し、APIの戻り値と画面の状態を「証拠（スクリーンショット）」と共に記録。
*   **コスト方針**:
    *   **原則**: AIへはテキストの報告書を読ませる（Vision APIは使わない）。
    *   **例外（UI問題）**: 「5px右にずらせばいい」など言葉で正確に伝えられる場合はテキストのみ。言葉での表現が難しいレイアウト崩れ・見た目の問題は、スクショを添付して判断を助ける。
    *   **判断基準**: 「言葉で十分に伝わるなら言葉で。迷ったらスクショで。」その場の開発AIに判断を委ねる。

### 4.2. 自動修復連携 (Repair Loop)
*   テスト失敗時、AIがそのまま読み込める形式で「テストレジストリ」へ失敗報告を出力。
*   **1回目・2回目の失敗**: 開発レジストリ側のAIへ修正を促す指示を作成。
*   **3回目の失敗（デッドロック）**: 自力での修復を断念し、Grok (xAI) への質問状（ドラフト）を自動作成。監督に判断を仰ぐ。

### 4.3. 安全装置 (Safety Guards)
*   **実行リミット**: 修正トライは最大**3回**。3回で改善しない場合は「デッドロック」として停止する。
*   **聖域の再検証**: 修正後、ターゲット以外の既存テスト（53項目等）も必ず全件通過することを確認。

### 4.4. 使い捨て報告書（チケット制）
*   **運用**: テスト報告書（`latest_report.md`）は、修正担当AIが修正をすべて完了し、次のテスト（答え合わせ）を受け入れる直前に削除する。
*   **哲学**: **「使い終わったら消す」**。報告書はその目的（修正の完了）を果たした瞬間に役目を終える。修正中は全情報を手元に置き、完了後に潔く手放す。

### 4.5. ゼロ摩擦セットアップ（One-Paste Setup）
*   **運用**: セットアップスクリプト（`scripts/setup.sh`）を1回実行するだけで環境が整う。
*   **監督がやること**: ブラウザでGitHubトークンを発行し、コピーする。スクリプトが「貼り付けてください」と表示したら**ペースト1回 → Enter**のみ。
*   **ATPが自動でやること**: トークンの`~/.zshrc`への書き込み、`.env`の生成、`.gitignore`への追加、GitHub接続確認まで一括実施。

### 4.6. GitHub Issue連携（方法B採用）
*   **テスト失敗時**: ATPが`vault-alchemist`リポジトリに「🔴 テスト失敗」のIssueを自動投稿。エラー詳細・証拠ログを添付。
*   **修正完了時**: 開発AIがIssueをCloseする。これがATPへの「再テスト開始」の合図となる。
*   **記録効果**: 全ての修正履歴がGitHub Issueとして永続的に蓄積される。

### 4.8. 自律改良ループ（Evolution Loop）★ NEW ★
*   **役割**: テストが全合格していても、定期的にコードを分析し「より良くなれる部分」を自律的に提案する。守るだけでなく、攻める。
*   **提案の生成**: 静的解析（重複検出・ESLint）の数値 + Grok APIのAI判断を組み合わせて生成。
*   **Issueのラベル**: `🔵 改善提案` — 修復ループの `🔴 テスト失敗` とは明確に区別。
*   **学習する提案**: Grokは「過去の採用記録」を読んだ上で次の提案を生成する。同じ提案を繰り返さない。
*   **採用記録**: 改善が採用・却下されるたびに `docs/（進化の記録）evolution-log.md` に自動追記。これが「世代」を構成する。
*   **聖域の不可侵**: 改善後も必ず53項目全合格を確認。聖域を壊す改善は採用しない。

## 7. この設計の致命的な弱点 / Critical Flaw
**「テストコード自体のバグに弱い」**
ATPが読み込んでいる「期待される結果」自体が間違っていた場合、AIは「正しいコードを間違っていると見なし、壊し続ける」リスクがある。そのため、テスト定義の修正には監督の承認が必須である。
