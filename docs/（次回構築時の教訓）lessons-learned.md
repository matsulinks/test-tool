# 🎓 次回（別プロジェクト）構築時の教訓リスト

ATP（Alchemist Test Pilot）の運用を通して得られた、**「最初から（監視対象側のプロジェクトに）設定しておくべき」**教訓のまとめ。
監視AI側（ATP）と開発AI側（テストを受ける対象）の連携をよりスムーズにするためのアーキテクチャ設計指針。

---

## 1. 失敗理由の明確化（Exit Codeの分離）

**【問題】**
シェルの終了コード（Exit Code）が1つ（例: `exit 1`）にまとめられていると、ATP側が「ビルドがこけたのか？」「テストがこけたのか？」「ヘルスチェックがこけたのか？」を即座に区別しづらい。

**【対策】**
最初からシェルやプロセスの段階ごとに、固有のExit Codeを割り当てておく。

```bash
# 例: setup.sh 等での明確な定義
exit 2  # テスト（ロジック）失敗
exit 3  # ビルド失敗（コンパイルエラーなど）
exit 4  # 疎通・ヘルスチェック失敗
```

これにより、ATP側で `error.status` 等を読み取るだけで、即座に次のアクション（エスカレーション先）を切り替えられる。

---

## 2. テスト結果のJSON出力（コンソールパースの脱却）

**【問題】**
ATPがコンソール（標準出力）の文字列を無理やりパースしてIssue本文や報告書（`latest_report.md`）を作ろうとすると、フレームワークの出力フォーマット変更に脆い。また、情報が欠落しやすい。

**【対策】**
監視対象（開発側）のテストフレームワーク設定で、最初から**「構造化データ（JSON）」**で結果をファイル出力するように仕込んでおく。

```javascript
// 例: vitest.config.ts に以下を1行追加するだけ
reporters: [
  'default', 
  ['json', { outputFile: 'tests/registry/latest_report.json' }]
]
```

ATP側は `latest_report.json` を読み込んでパースするだけで済むようになり、複雑で壊れやすい正規表現やコンソールスクレイピングのロジックを全廃できる。

---

## 3. Node.js バージョン要件の明示（`engines` と `.nvmrc`）

**【問題】**
ATP側（セットアップスクリプト）で「v22以外は即エラー」と弾いていたが、監視対象のプロジェクト側にその要件がシステムとして明示されていなかったため、CI連携時や別環境構築時に不整合が発生しやすかった。

**【対策】**
最初からパッケージのルート構成情報として縛りを明示し、環境のブレを許容しないようにする。

```json
// 例: package.json に明記
{
  "engines": {
    "node": ">=22"
  }
}
```
さらに、プロジェクトルートに `.nvmrc`（中身 `22`）を置いておき、自動的にバージョンが沿うように設計しておく。

---

**総括:**
次にATP型のシステムを他プロジェクトに横展開するときは、**「ATP側で頑張ってパース・推測する」**のではなく、**「監視される側のプロジェクトにあらかじめ『機械が読みやすい構造化データやコード』を出力させる」**という設計思想を持つことが最重要となる。
