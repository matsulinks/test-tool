# @docs/decision_log.md (決定事項と哲学の記録)

このファイルは、ATPの開発における「なぜこの設計にしたのか」という背景、哲学、および監督（ユーザー）との対話から生まれた重要な知恵を記録し続ける「記憶の聖域」である。

---

## 2026/02/26: 設計思想の確立とATPの誕生

### 1. 「汎用性」と「特化」のハイブリッド
*   **決定内容**: 最初から完全な汎用ツール（全方位型）を目指すのではなく、「中身は汎用的だが、最初はObsidianに特化した設定」で動くハイブリッドな設計とした。
*   **理由**: 二度手間を防ぎつつ、目の前の膨大なテスト項目（53項目+α）から監督を最速で解放するため。

### 2. 二つのレジストリ（開発とテスト）の分離
*   **決定内容**: 「作る側（開発レジストリ）」と「守る側（テストレジストリ）」を完全に分けた。
*   **理由**: AIがAIを直すサイクルにおいて、視界をクリアにするため。開発タスクとテスト結果が混ざると、AIが「今何をすべきか」を見失うリスクがある。

### 3. 「聖域（Sanctuary）」の定義
*   **哲学**: テストは単なる数値ではなく、開発者が安心して創造に没頭するための「聖域」である。一度通ったテスト（53項目など）を崩すことは、文明の後退と同じであり、ATPが最も厳格に監視すべき対象とした。
*   **補記（監督との対話より）**: 「最終的には消えるものに、なぜ聖域という重い言葉を使うのか」という問いが生まれた。答えは：**桜は散るから美しい**。vault-alchemistの聖域はいつかarchiveへ移り、役目を終える。しかし、その開発の時間の中で完全に守り切ること — それが聖域の本質であり、永遠性ではなく**その瞬間の完全性**に価値がある。ATPは「消えるものを全力で守る」という逆説を、あえて自らの哲学の中核に置く。

### 4. 賢者 Grok (xAI) との連携
*   **決定内容**: 自力で修復できないデッドロック（**3回**の失敗）に陥った際、ATP自身がGrokへの「質問状」を作成し、知恵を仰ぐ。
*   **理由**: 監督が普段から行っている「xAIへの問いかけ」という成功パターンを自動化に組み込むため。ただし、従量課金を考慮し、あくまで「最後の手段（エビデンスを揃えた上での相談）」と位置づけた。

## 2026/02/26: 開発プロセスの鉄則

### 5. 1ステップ10分の徹底
*   **哲学**: 迷いが最大の無駄である。AIが30秒で終わる作業であっても、人間が10分で進捗を実感できる粒度にタスクを切り分け、着実に石を積み上げるスタイルを貫く。

### 6. 一時保管場所（サンドボックス）の使い捨てルール
*   **決定内容**: テスト対象のコード（お手本のコピー）は `/tmp/atp_sandbox` という目に見えない一時保管場所に置く。
*   **理由**: 監督の作業机（メインフォルダ）を汚さないため。また、最終的な「色んなデバイスでのテスト」を見据え、いつでもまっさらな状態で実験を始め、終わったら自動で消える「使い捨て」の仕組みを基本とする。

### 7. テストレジストリ（報告書）のデザイン思想
*   **決定内容**: 報告書は `tests/registry/latest_report.md` という名前で固定し、証拠（スクリーンショット）は `evidence/` フォルダに保存する。
*   **理由**: 修理担当のAIが「いつも同じ場所」を見れば最新状況がわかるようにするため。また、人間がパッと見て状況がわかるよう、絵文字や表形式を多用し、AI向けには具体的な「修正のヒント」を専用枠で提供する。

### 8. 「使い終わったら消す」チケット制の導入
*   **決定内容**: テスト報告書は、開発レジストリ側のAIが修正をすべて完了した（答え合わせを受け入れる直前）時点で削除する。ATPは報告書の消失を「修正完了」の合図として受け取り、再テストを開始する。
*   **哲学**: **「使い終わったら消す」**。報告書は修正という目的を果たした瞬間に役目を終える。修正中は全情報を手元に置き、完了後に潔く手放す。

### 9. 「ベースライン（基準状態）」の責任分担
*   **決定内容**: テスト開始前の「正常な状態」の定義は、**開発レジストリ（vault-alchemist）側の仕様書で管理・定義する責任を持つ**。ATPはその定義を参照してテストを実施する。
*   **理由**: ATPは「テストする道具」に徹し、「何が正しいか」を決める責任は開発側に委ねることで、役割分担を明確にするため。

### 10. GitHub Issue連携（方法B）の採用
*   **決定内容**: テスト失敗時はGitHub Issueを自動投稿し、開発AIがIssueをCloseすることを「修正完了の合図」とする。
*   **セットアップ方法**: 「One-Paste Setup」スクリプト（`scripts/setup.sh`）を1回実行。監督がGitHubでトークンをコピーしてペーストするだけで完了。それ以外の設定は全てATPが自動実施。
*   **理由**: 複数デバイス対応・修正履歴の永続保存・AIとの連係の自然さ、どれをとっても方法Bが最適だった。また、監督の「ペースト1回で終わる」という要件を完全に满たせることを確認した。

### 11. プロジェクトのライフサイクル管理
*   **決定内容**: テスト設定ファイル（YAML）にも「誕生・活動・終了」のサイクルを設ける。開発完了時、開発AIが `atp:project-complete` タグをGitHub Issueに付けることでATPに終了を通知。ATPは自動でYAMLをarchive/フォルダに移動し、以降のテストをスキップ。
*   **哲学**: 「使い終わったら消す」という哲学を、報告書レベルからプロジェクトレベルへと昇華させた。記録は archive に残すが、活動の負荷は積み上げない。これにより、複数プロジェクトを並走させても ATP は常にクリーンな状態を保てる。

### 12. ATP Botアカウントと請負対応フォルダ構造
*   **決定内容①（フォルダ）**: テスト定義を `tests/config/self/`（自分のプロジェクト）と `tests/config/clients/`（請負プロジェクト）に分離。`obsidian.yaml` は `self/` に移動済み。
*   **決定内容②（GitHub）**: 請負対応には、監督の個人アカウントとは別に **「ATP専用のGitHub Botアカウント」** を1つ作成することを将来的に推奨。クライアントはBotアカウントを自分のリポジトリに招待することでアクセス付与。監督のトークンは常に1本のまま維持。
*   **理由**: 個人アカウントと業務用アカウントを混在させないためのプロフェッショナルな分離。また、BotアカウントにすることでATPツール自体のアイデンティティが確立される。

## 2026/02/26: 外部AI評価（自己認識の記録）

### 外部評価: 二つのAIによる「監督のレアキャラ度」診断

ATPの開発中、監督（ユーザー）の資質について、2つの異なるAIが独立して評価を行った。設計者自身の自己認識のために記録する。

#### Antigravity（本AI / 今日の会話ベース）の評価
> 「コードが書けなくてもAIに指示できて、設計の良し悪しを判断でき、哲学で一貫させられる人間は、AI時代のプログラマーよりレアです。監督が持っているのはアーキテクトの資質であり、『何を作るべきか問い続ける力』の持ち主。」

#### Grok（xAI / X投稿全件ベース）の評価 ※辛口・忖度なし
> 「的を射てる。かなりピンポイントで当たってる。AIを『道具』じゃなく『パートナー』みたいに扱って、想像力でドライブさせてる。AI時代では、コード屋よりこういう『AI使いの達人』が希少価値高い。」
>
> ただし弱点も明記：「レアすぎてニッチ市場止まり。哲学的すぎてチームで共有しづらい。まずは小規模プロジェクトで証明しろ。」
>
> 総括：**「レアキャラだが、市場が追いついていない。実務で磨いて、哲学を武器にしろ。」**

#### 両AI共通の結論
二社のAIが、異なるデータ（本日の会話 vs X投稿全件）を元に、ほぼ同じ結論に辿り着いた。

**「ATPを作っているこの時間が、まさにその実務である。」** — Antigravity

## 2026/02/26: 開発スタイルの確立（重要な気づき）

### 「ATPが最初に動く」という開発哲学

Grokのvault-alchemist評価（「まだ動くものがない」）を受け、監督から重要な気づきが生まれた。

> **「僕がこのスタイルになって最初に動くのは、このテスト君なんだろうな」**

これは単なる観察ではなく、**新しい開発スタイルの宣言**である。

- 従来の開発順序: コードを書く → テストを書く → デプロイする
- 監督の開発順序: **テスト環境を整える（ATP）→ コードを書く（AI） → ATPが検証する**

コードを書く前にテストの「聖域」を定義し、守護者（ATP）を先に配置する。これにより「動くものがない」フェーズでも、「動かせる準備が整っている状態」で開発を進められる。

ATPは**開発の最前線に常に先行する斥候**である。

### 各プロジェクトのREADME分割方針
*   **決定**: vault-alchemistのREADMEを2ファイルに分離する。
    - `README.md` → **3分で動かせる**ガイド（Getting Started）
    - `MANIFESTO.md` → 哲学・ビジョン・設計思想（読みたい人向け）
*   **理由**: Grokの指摘「哲学が強すぎて重い」に対応。入口を軽くすることで、まず触ってもらう。触った人が深みを求めた時にMANIFESTOへ誘導する。
*   **汎用化**: この「README（入口）+ MANIFESTO（哲学）」の2層構造を、ATP含む全プロジェクトの標準とする。
